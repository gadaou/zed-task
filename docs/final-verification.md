## 8. Known intentional limitations

These are **scope boundaries**, not defects. Each is explicitly disclosed in `FINAL_REVIEW.md` §5 and `PROJECT_SPEC.md` Bonus features.

1. **Payment gateways are dummies only.** Only `dummy_success`, `dummy_failing`, `dummy_timeout` are registered. No real Stripe/HyperPay/Tabby/Moyasar integration. Adding one is documented in `docs/payment-gateways.md`.
2. **Identity is asserted via `X-User-Id` header.** No real bearer/JWT validation is performed by Django; this is the API-gateway's responsibility per `PROJECT_SPEC.md` §4.3.
3. **Scale is unproven beyond unit/integration tests.** No load-testing artifact in the repo. The architecture is *built to scale* (Redis locks, idempotency, atomic stock, Celery, `tenant_id`-leading composite indexes) but capacity claims are stated as initial targets.
4. **B2B is lightweight metadata only.** Three optional snapshot fields (`company_name`, `tax_number`, `purchase_order_reference`). No approval workflows / net-N terms / multi-line shipping splits / creator-approver roles.
5. **Catalog is a local model.** No remote catalog-service integration.
6. **Tenant isolation is application-layer.** PostgreSQL Row-Level Security (RLS) is on the roadmap (`PROJECT_SPEC.md` §9.7), not yet implemented.
7. **Order listing / status polling endpoints are deferred.** `GET /api/v1/orders/{id}/` is not wired in this iteration.
8. **Public invoice retrieval is via Django admin / `MEDIA_ROOT`.** Public REST endpoint for invoice PDF download is planned for a future iteration.
